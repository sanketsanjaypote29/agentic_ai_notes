Educosys Claude - Architecture & Design Notes

Layered Architecture

The codebase is split into discrete layers. Each layer has one job. No layer reaches across to another layer's internals.

CLI / REPL The entry point. Responsible for talking to the user - receiving input, displaying output, managing commands. Nothing below this layer knows about the user.
↓
Agent Responsible for reasoning and decision-making. Takes a question, decides what to do, calls tools if needed, returns an answer. The "brain" of the system.
↓
Tools Responsible for giving the agent hands. Each tool is one capability - search the codebase, read a file, run a command. The agent decides when to use them.
↓
Skills Responsible for higher-level composed capabilities. A skill combines multiple tools and agent calls into one reusable workflow - e.g. "explain this PR" or "review this file". Skills are what end-users think of as features.
↓
MCP Responsible for external integrations. MCP servers expose third-party systems (GitHub, Jira, Slack) as tools the agent can call. Keeps integration logic separate from core agent logic.
↓
Context / RAG Responsible for knowledge retrieval. Knows how to index a codebase and find relevant pieces of it given a query. Completely unaware of the agent or tools above it.
↓
Memory Responsible for remembering. Short-term keeps the current conversation. Long-term keeps facts, summaries, and behavioral patterns across sessions.
↓
Safety Responsible for guardrails. Validates inputs before they reach the agent and outputs before they reach the user. Blocks harmful content, enforces scope, prevents prompt injection. Nothing leaves the system without passing through here.
↓
Freshness Responsible for keeping the index up to date. Detects when the codebase has changed and triggers re-indexing. Without this, the RAG layer answers questions about stale code.
↓
LLM Responsible for model access. Decides which LLM and embedder to instantiate. Everything above this layer is model-agnostic.
↓
Config Responsible for application-wide settings. A single source of truth for how the system is configured - providers, modes, limits. Every layer reads from it, nothing writes to it at runtime.
↓
Observability Responsible for visibility. Structured logging so you can see exactly what the system is doing at runtime - which layer, which operation, which outcome.
↓
Eval Responsible for measuring quality. Shared golden datasets test every layer independently - retrieval (Recall@k, MRR), context (precision, recall), generation (faithfulness, relevancy via RAGAS), and agent (task success rate, step accuracy).

Package & Dev Tooling

Poetry vs pipx

We use poetry install for development - it installs the package in editable mode so code changes reflect immediately without reinstall. pipx is for distributing a finished CLI tool to end-users.

Decision
Use poetry run educosys_claude during development. Use pipx to test the installed package from another directory.

config.yaml vs .env - what goes where and why

config.yaml and .env serve completely different purposes and should never be mixed.

config.yaml - behaviour config
Controls how the app behaves: which LLM provider, which vector store, model names, chunk sizes, collection names, memory limits. Safe to commit to git. Changes here switch features, not credentials.
.env - secrets
API keys, passwords, URLs that change per environment (dev vs prod). Never committed to git - always in .gitignore. Read via os.getenv() at runtime, not loaded into the config dict.
Why separate?
A teammate can clone the repo, see exactly how the app is configured in config.yaml, and supply their own keys in .env. If secrets lived in config.yaml, one accidental commit leaks every key. If behaviour config lived in .env, there's no visible record of what settings the app runs with.
