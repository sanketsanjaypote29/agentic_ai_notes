Memory in Agentic AI Systems

How agents store, retrieve, and manage information - within a session and across sessions.

📌 LLMs are Stateless

By default, LLMs are completely stateless. Every call is independent - the model has no memory of prior conversations, no awareness of who the user is, and no knowledge of what it did in a previous session. Each request starts from zero. Memory is the layer engineers add on top to give agents continuity, personalization, and the ability to reason across time.

Two fundamental layers: Short-term memory handles the current task or session. Long-term memory persists facts, events, and skills across tasks and sessions. Production agentic systems need both.

Short-Term Memory

Everything relevant to the current task or session - conversation history, current plan, tool outputs, intermediate reasoning, agent state.

Session-scoped

Long-Term Memory

Information retained across tasks and sessions - user facts, past events, skills, and workflows. Survives indefinitely.

Cross-session

⚡ Short-Term Memory (Working Memory)

Short-term memory holds everything relevant to the current task or session. It is typically assembled into the context window before each LLM call, giving the model direct, zero-latency access to the current working state.

  • Conversation history - all prior user and assistant turns in the session
  • Current plan - active task list, goals, and next steps
  • Tool outputs - API responses, code execution results, search outputs
  • Scratchpad - intermediate reasoning and chain-of-thought steps
  • Agent state - workflow position, loop counters, execution flags
  • Working context - retrieved docs or preferences injected for this call

Storage - not just RAM

Short-term memory is not necessarily stored only in RAM. It can be persisted to durable storage and still be short-term, as long as it belongs to the current task or session and is not intended as permanent cross-session knowledge.

Common storage backends

  • RAM / in-process dict
  • Redis (fast, ephemeral)
  • SQL / NoSQL checkpoints
  • Workflow state stores (LangGraph, Temporal)
  • File-based checkpoints for long-running agents

Key characteristic

The defining property is scope, not storage medium. If the data belongs to a current task and will not be consulted in future sessions as permanent knowledge, it is short-term - regardless of where it lives physically.

🗜 Managing Large Short-Term Memory

As conversations and agent executions grow, context can exceed the model's context window. These are the common techniques, and most production systems combine several of them.

1
Sliding Window
Keep only the most recent N messages.
Keep last 20 messages Discard older messages
Simplest approach O(1) management

Pros

  • Simple to implement
  • Fast - no extra LLM calls
  • Zero cost overhead

Cons

  • Important older information is discarded
  • No compression - just truncation
2
Rolling Summarization
Periodically compress older messages into a running summary.
100 messages ↓ 1 summary + recent messages
Token reduction Preserves gist

Pros

  • Significant token reduction
  • Preserves important information
  • Maintains conversational continuity

Cons

  • Summary may lose fine-grained details
  • Errors can accumulate over many summarization cycles
  • Extra LLM call per summarization
3
Message Trimming
Remove low-value messages that add no signal.
Greetings, "thank you" messages, repeated confirmations → remove
Easy token savings No LLM cost

Pros

  • Easy wins - often 5–20% token savings
  • No additional LLM calls

Cons

  • Requires heuristics to identify low-value content
  • Heuristics can misfire on edge cases
4
Semantic Recall
Move older history into a vector database - retrieve only what's relevant.
Current query: "What project was I working on?" ↓ Embed query ↓ Search vector store of past messages ↓ Retrieve: "Last week user discussed educosys.com" ↓ Inject into context
Vector DB Embedding search Fuzzy recall

Pros

  • Scales to very large histories
  • Only relevant information is injected
  • No hard token limit on total history

Cons

  • Retrieval quality depends on embeddings and search
  • May miss relevant context if query is poorly phrased
  • Added retrieval latency
5
State Extraction
Extract structured key facts instead of storing raw messages.
{ "name": "Keerti", "goal": "Build educosys.com", "preferred_language": "Python" }
Structured state Token efficient

Pros

  • Extremely token efficient
  • Easy to maintain and update
  • Deterministic retrieval - no embedding needed

Cons

  • Works best for structured, factual information
  • Doesn't preserve full conversational detail
  • Requires extraction logic
6
Hierarchical Summarization
Create summaries at multiple levels - for extremely long conversations.
100 Messages ↓ 10 Summaries (per chunk) ↓ 1 Higher-Level Summary
Multi-level RAPTOR-style

Pros

  • Handles extremely long conversations
  • Coarse summaries for high-level questions
  • Leaf summaries for detail questions

Cons

  • Risk of information loss across layers
  • Multiple LLM calls per compression cycle
7
Context Compression
Use an LLM to rewrite history into a shorter, information-dense representation.
Original: 5000 tokens Compressed: 800 tokens
LLM-compressed High fidelity

A smaller or cheaper model rewrites the conversation history, preserving nuance that simple summarization loses. More detailed than a bullet-point summary.

Pros

  • More detailed than simple summarization
  • Preserves tone, intent, and nuance

Cons

  • Additional LLM cost per compression
  • Compression may introduce subtle errors

🏭 Common Production Pattern

Most modern agentic systems combine multiple approaches. Relying on any single technique is rare. The most common hybrid pattern:

Recent Messages ← sliding window of last N turns + Running Summary ← rolling compression of older turns + Retrieved Memories ← semantic recall from vector store + Structured State ← extracted user profile / preferences
Example: Keep the last 10 messages verbatim + a running conversation summary + relevant memories retrieved from history + user profile (name, goal, preferred language). This covers recency, compression, fuzzy recall, and structured facts - all in one context.

🗄 Long-Term Memory

Long-term memory persists outside the context window in external stores. It survives across sessions, and is selectively retrieved into context when relevant.

Personalization

The agent knows the user's preferences, role, and history without re-asking on every session.

Historical recall

Past events, prior decisions, and completed tasks are accessible across sessions and agents.

Knowledge retention

Domain facts, SOPs, and learned workflows persist and can be reused without re-derivation.

The three long-term memory types

The distinction is conceptual, not storage-based. All three may be stored in the same database. What differs is the type of information they represent.

🟢 Semantic Memory
Stores facts and knowledge - what the agent knows. Does not depend on when it was learned.
Question answered: "What do I know?"
🔵 Episodic Memory
Stores events and experiences - what happened, when, with whom. Enables recall of prior interactions.
Question answered: "What happened before?"
🟡 Procedural Memory
Stores skills and workflows - how to do things. Instructions, SOPs, and behavioral patterns.
Question answered: "How do I do it?"

Episodic Memory - Events & Experiences
Records of past events - what happened, when, with whom.
Past interactions Completed tasks Time-stamped events

Examples

  • User completed a course last week
  • Previous conversation summaries

Common storage

  • Conversation History archives
  • SQL Database (filter by date/user)

Procedural Memory - Skills & Workflows
How to do things - instructions, SOPs, and behavioral rules the agent should follow consistently.
SOPs Prompt templates Workflow definitions

Examples

  • Customer support escalation workflow
  • Monthly reporting process
  • Coding standards and style guides
  • User's preferred output format
  • Custom tool-use patterns

  • SOP Repositories
  • Prompt Templates
  • System Prompt (injected directly)
  • SQL Database (versioned workflows)

💡Type vs Storage

The distinction between semantic, episodic, and procedural memory is primarily conceptual, not storage-based. In production systems, all three may coexist in the same database.

Semantic → Facts (what I know) Episodic → Events (what happened) Procedural → Workflows (how to do it)
The difference is not where they are stored, but what type of information they represent. A vector database can hold all three types. A SQL table can hold all three types. Type is about semantics - not infrastructure.
