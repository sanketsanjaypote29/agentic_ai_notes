Ranking in RAG

Retrieval Ranking · Fusion Ranking · Re-ranking — end to end

What is Ranking?

When a user sends a query to a RAG system, there are potentially millions of documents in the corpus. Ranking is the process of ordering documents by how relevant they are to the query — so the best documents reach the LLM and the noise does not.

Without ranking, the LLM receives a random or arbitrary selection of chunks. With ranking, it receives the most relevant, diverse, and high-quality context — which directly determines the quality of the generated answer.

Ranking in RAG is not a single step. It can happen at up to three distinct stages, each with a different purpose, different cost, and critically — running in a different location. Some stages happen inside the database, others happen in your application code. Not all three are required — the simplest pipeline uses only retrieval ranking. Fusion is added when you have multiple retrievers. Re-ranking is added when you need higher precision and can afford the cost.

Inside the Vector DB / Search Engine
Stage 1 — Retrieval Ranking
The DB scores and orders documents internally using BM25, cosine similarity, dot product, etc. Your app only sees the output — a ranked Top-K list. You do not control this ranking directly; you choose the retriever and its parameters.
Top-K results returned to your application
Outside the DB — in your Application / RAG Orchestration Layer
Stage 2 — Fusion Ranking
Your app receives ranked lists from multiple retrievers (BM25 + vector). It merges them using RRF or weighted fusion. No model inference. Runs in your orchestration code (LangChain, LlamaIndex, custom).
Stage 3 — Re-ranking
Your app calls a cross encoder or reranker API on a candidate set (however many you retrieved). The reranker reads each (query, document) pair and assigns a precise relevance score. Runs as a separate ML model call in your pipeline.

Retrieval Ranking

The first ranking stage — happens inside the retrieval system itself (vector database or search engine) before anything else sees the results.

Input

A user query string

Output

Top-K documents ranked by relevance score

Algorithms

Sparse / Lexical Methods

BM25 (Best Match 25)

Term-frequency based ranking. The standard for keyword search. Used heavily in Elasticsearch and OpenSearch. Penalizes over-repetition of terms (saturation) and accounts for document length.

Score(D, Q) = Σ IDF(qi) × [ f(qi,D) × (k1+1) ] / [ f(qi,D) + k1 × (1 - b + b × |D|/avgdl) ]
No neural model Fast Exact term match

TF-IDF

Predecessor to BM25. Weights terms by how frequent they are in the document vs how rare across the corpus. Still used in simpler pipelines.

Score = TF(t,d) × log(N / df(t))

SPLADE

Learned sparse representations. Expands query/document with related terms using a transformer, but keeps the output in a sparse bag-of-words format. Best of both worlds: semantic + sparse efficiency.

Transformer-based Sparse output

Dense / Semantic Methods

Cosine Similarity

Measures the angle between query and document embedding vectors. Range: −1 to 1. Most common metric for dense retrieval. Normalizes vector magnitude.

cos(θ) = (A · B) / (||A|| × ||B||)
Dense vectorsNormalized

Dot Product (Inner Product)

Faster than cosine similarity. Does not normalize — magnitude matters. Used when embeddings are already normalized (e.g., OpenAI embeddings), in which case it's equivalent to cosine.

Score = A · B = Σ AᵢBᵢ
FastestMagnitude-sensitive

DPR (Dense Passage Retrieval)

Dual-encoder model. Query encoder and passage encoder trained separately with contrastive learning. Query and document embeddings are computed independently, enabling precomputed document indices.

Score = E_query(q) · E_passage(p)
Bi-encoderFAISS-compatible

ColBERT (Retrieval mode)

Late interaction model. Encodes every token in query and document separately, then computes MaxSim: for each query token, find the most similar document token.

Score = Σq max_d (Eq · Ed^T)
Token-levelLate interactionScalable
Where Retrieval Ranking Runs
Elasticsearch OpenSearch Pinecone Qdrant Weaviate Milvus
Example — Query: "How does Kafka replication work?"
BM25 output: 1. Doc A   2. Doc B   3. Doc C
This stage is cheap and fast — it narrows thousands of documents down to Top-K candidates.

Fusion Ranking

Problem: Different retrievers find different relevant documents. We want to combine multiple ranked lists into a single, better list — without re-reading any document text.

The Problem Illustrated
BM25 Results:
1. Doc A  ← keyword match
2. Doc B
3. Doc C
Vector Search:
1. Doc C  ← semantic match
2. Doc A
3. Doc D  ← only found here

Doc D only appears in vector search. Doc A appears in both but at different ranks. Fusion merges these intelligently.

Algorithm 1 — Reciprocal Rank Fusion (RRF)

The most popular fusion method in modern RAG. Simple, robust, and parameter-free (except k). Invented by researchers at Google/Waterloo.

Score(doc) = Σ  1 / (k + rank_i(doc))

where:
  k     = constant (typically 60) to dampen high-rank dominance
  rank  = position in retriever i's ranked list (1-indexed)
  Σ     = sum across all retrievers

Worked Example

Doc A: BM25 rank=1, Vector rank=2
  RRF = 1/(60+1) + 1/(60+2) = 0.01639 + 0.01613 = 0.03252

Doc C: BM25 rank=3, Vector rank=1
  RRF = 1/(60+3) + 1/(60+1) = 0.01587 + 0.01639 = 0.03226

Doc D: only in Vector rank=3
  RRF = 1/(60+3) = 0.01587

Final order: A → C → B → D
Why k=60? Prevents a document ranked #1 from dominating over documents ranked #2 or #3. The difference between rank 1 and rank 2 shrinks as k grows.
Algorithm 2 — Weighted Score Fusion

Combines raw scores directly. Requires scores to be on comparable scales (normalize first). α is a tunable hyperparameter.

Final Score = α × BM25_score + (1 - α) × Vector_score

Example: α = 0.4
  Final = 0.4 × BM25 + 0.6 × Vector
Gotcha: BM25 scores are unbounded; vector similarity is typically −1 to 1. Min-max normalize each before combining, or use RRF to avoid this problem.
What Fusion Does and Does NOT Do
  • Combines rankings from multiple retrieval systems
  • Surfaces documents missed by one retriever
  • Extremely cheap — no model inference
  • Does NOT read document text
  • Does NOT run a neural model
  • Does NOT reassess relevance semantically
  • Does NOT understand query meaning

Re-ranking

Problem: The retrieved Top-100 documents still contain noise. We need a stronger, slower model to actually read query + document pairs and assign precise relevance scores.

Input

(Query, Document) pair

Output

Relevance score per pair → re-ordered list

Example:
Query → Doc A = 0.71  |  Doc B = 0.32  |  Doc C = 0.95  |  Doc D = 0.87
Final order: Doc C → Doc D → Doc A → Doc B
Algorithm 1 — Cross Encoder (Most Important)

How it works

Both query and document are concatenated and fed into a transformer together. Self-attention can attend across query and document tokens — capturing deep interactions impossible in bi-encoders.

[CLS] Query [SEP] Document [SEP]
↓
Transformer (full attention)
↓
Relevance Score (0 to 1)

Popular Cross Encoders

  • BGE Reranker (BAAI) — open source, state of the art
  • Cohere Rerank — hosted API, easy integration
  • MonoT5 — T5-based sequence-to-sequence reranker
  • ms-marco-MiniLM — lightweight, fast
Trade-off: Cross encoders are the most accurate method — but you must run one forward pass per (query, document) pair. For 100 candidates, that's 100 inference calls. Keep candidate pool manageable (Top-50 to Top-100).
Algorithm 2 — ColBERT Re-ranking

Late Interaction

Encodes query and document separately (like bi-encoders), but stores per-token embeddings. At query time, computes MaxSim between every query token and every document token.

Score = Σ_qi  max_dj  (Eq_i · Ed_j)

For each query token: find the best matching document token.
Sum across all query tokens.
  • More accurate than standard bi-encoders
  • Faster than full cross encoders
  • Document embeddings precomputed offline
  • Used in: RAGatouille, ColBERT v2
Algorithm 3 — Learning-to-Rank (LTR)

Feature-based ML ranking

Instead of running a transformer, extract hand-crafted features per (query, document) pair and train a gradient-boosted model or neural ranker on click/relevance data.

Features per pair:
  - BM25 score
  - Embedding cosine similarity
  - Document length
  - Freshness / recency
  - Click-through rate
  - Popularity / page rank
  ↓
XGBoost / LightGBM / Neural ranker
  ↓
Relevance score

Common LTR Models

  • RankNet — pairwise neural ranking (early work from Burges)
  • LambdaMART — gradient boosted trees, optimizes NDCG directly
  • XGBoost Ranker — fast, widely used in production
  • ListNet / ListMLE — listwise approaches
Very fast inference Needs training data Good for personalization
Algorithm 4 — MMR (Maximal Marginal Relevance)

Diversity-aware re-ranking

Addresses a common RAG failure: retrieving many nearly-identical chunks. MMR greedily selects documents that are relevant to the query AND dissimilar to already-selected documents.

MMR(d) = λ × Sim(d, query) - (1-λ) × max_{d' ∈ S} Sim(d, d')

where:
  S   = already selected documents
  λ   = relevance vs diversity trade-off (0 to 1)
  Sim = cosine similarity

WITHOUT MMR

Chunk A   (score 0.92)
Chunk A'  (score 0.91)
Chunk A'' (score 0.90)
Chunk A'''(score 0.89)
→ All near-duplicates!

WITH MMR

Chunk A   (relevant)
Chunk B   (different angle)
Chunk C   (new info)
Chunk D   (covers gap)
→ Diverse context!
Why it matters for LLMs: Sending near-duplicate context wastes your context window and causes the LLM to hallucinate confidence in repeated facts. MMR gives the LLM broader coverage.

Stage Comparison

Stage Purpose Reads Doc Text? Runs Neural Model? Cost Typical Scale
Retrieval Ranking Find candidate documents from corpus No (uses index) No (BM25) / Yes (DPR) Low Millions → Top-100
Fusion Ranking Combine multiple ranked lists No No Very Low N × Top-100 → Top-100
Re-ranking Recompute relevance with stronger model Yes Yes High Top-100 → Top-5/10

Design rationale: Retrieval is cheap — cast a wide net. Fusion is free — combine signals. Re-ranking is expensive — run it on a small set. LLM generation is most expensive — only feed it the best 5–10 docs to minimize hallucination and token cost.
