Context Engineering

How language models use context, how position shapes attention, and how to engineer the context window for maximum accuracy.

📌 What is the Context Window?

Every time an LLM processes a request, it reads a finite block of text - the context window. Everything the model "knows" during that call comes from exactly two sources: its pre-training weights (frozen, general knowledge) and the context window (dynamic, call-specific information you supply).

As an AI engineer, you have no control over the weights. The context window is your entire design surface.

The context window is the maximum number of tokens an LLM can read in a single forward pass. Tokens include everything: system prompt, conversation history, retrieved documents, tool call results, and the model's own generated response.

⚠ Tokens in the output count too - every token the model generates reduces the space available for input on the next turn. A long response shrinks your remaining context budget.

🗂 The Four Zones of a Context Window

Think of the context window as a structured document with four distinct zones. Each serves a different purpose and has different management strategies. Example: gpt-4o at 128,000 tokens, assembled per-call by your agent.

🔧 System Prompt
Role definition, agent persona, rules, tool descriptions, output format instructions. Static or semi-static - set once per agent type.
~500–2k tokens
💬 Conversation History
All prior turns (user messages + assistant responses) in this session. Grows with each turn - must be managed or it overflows.
~1k–20k tokens
📚 Retrieved Context
Chunks fetched by the RAG pipeline - documents, code, knowledge base content relevant to this specific query. Dynamic per query.
~2k–10k tokens
🛠 Tool Outputs
Results from function/tool calls the agent made - API responses, code execution outputs, search results, database query results.
~500–5k tokens
👤 Current User Query
The current user message. Placed last - leverages the recency effect for maximum attention during generation.
~50–500 tokens

⚠️ Lost in the Middle Problem

LLMs exhibit a "lost in the middle" behavior - information at the beginning and end of a long context is utilized more effectively than information buried in the middle. Retrieval accuracy follows a U-shaped curve.

Accuracy High ──╮ ╭── ╲ ╱ ╲ ╱ Low ╰╯ Start Middle End

Reference: "Lost in the Middle: How Language Models Use Long Contexts" (Liu et al.) - models performed best when relevant information appeared near the start or end, and worst when it appeared in the middle.

1. Recency Effect (End of Context)

The end of the context is given higher importance because of how transformer-based generation works. When generating the next token, the model attends to all previous tokens, but the most recent tokens are closer to the current generation step and easier to utilize. This effect is driven by transformer architecture and generation dynamics.

[ Long Context ] [ Long Context ] [ Long Context ] User Question ← appears at the end → highly influential

2. Primacy Effect (Beginning of Context)

The beginning-of-context advantage is not built into the transformer architecture - it emerges from training. During pretraining, documents frequently start with titles, headings, introductions, and summaries. During instruction tuning, prompts often begin with:

You are a helpful assistant. Follow these rules...

As a result, the model learns that early tokens often contain critical information. This effect is primarily a learned behavior rather than an architectural property.

3. Why is the Middle Weaker?

As context length increases:

  • Attention must be distributed across more tokens
  • Relevant information competes with irrelevant information
  • Retrieval of information from the middle becomes less reliable

The information is not forgotten, but the probability of successfully utilizing it decreases compared to information near the beginning or end.

🏗 Context Architecture Patterns

This is one of the most interesting parts of context engineering. When people say "Context Architecture", they're asking: How is the final prompt/context assembled before every LLM call? Production systems usually have these patterns.

Static → Conversational → Knowledge-Augmented → Agentic.

🧠 Memory in AI Agents - Why Is It Needed?

Every LLM call starts from a blank slate. The model has no inherent awareness of who the user is, what happened in previous sessions, or what it did an hour ago. Without memory, every conversation is stateless - the agent cannot learn, personalize, or reason across time.

Multi-session continuity

Users expect the assistant to remember past conversations, preferences, and decisions - not repeat the same onboarding questions every time.

Personalization

Facts about the user (role, preferences, history) make responses more relevant and reduce cognitive load - the agent doesn't ask what it already knows.

Long-running agents

Agentic tasks spanning hours or days cannot fit their full history in one context window. Memory lets the agent pick up where it left off.

Context window is finite

Even 128k tokens run out. Memory externalizes information so the context window holds only what's needed right now.

Avoiding repetition

Without memory, the agent rediscovers the same facts, re-asks the same questions, and makes the same errors across sessions.

Cross-session reasoning

Some conclusions require synthesizing information from many past interactions - impossible without a store that persists beyond a single context window.

⚡ Short-Term Memory (Session Memory)

Session-scoped memory covering recent interactions.

What it holds

  • Conversation turns (user + assistant)
  • Tool call results from this session
  • Current task state and partial results
  • Intermediate reasoning / chain-of-thought

Overflow management

  • Sliding window — keep last N turns
  • Rolling summarization — compress old turns
  • Write-to-long-term — extract key facts before eviction
Short-term memory can be persisted indefinitely — many frameworks keep it in a DB. "Session-scoped" refers to usage scope, not storage lifetime.

🗄 Long-Term Memory (External Memory)

Persists across sessions in an external store. Selectively retrieved into the context window when relevant. Scales beyond any token limit — trades perfect recall for scalability.

Episodic

Records of past events — what happened, when, with whom.

Event-based

Semantic

Facts and user-specific knowledge independent of when learned.

Fact-based

Procedural

Skills, workflows, and behavioral rules to follow consistently.

Behavior-based
Four operations: Write (store at session end or on trigger) → Read (retrieve top-K at query time) → Update (overwrite stale facts) → Delete (hygiene, deduplication, user-triggered forget).

🔀 The Context Management Pipeline

Now that we understand what goes into context and how different architectures assemble it, the question is: how do we engineer the contents of each zone to be as useful as possible? Effective context engineering is a pipeline - each stage transforms the raw information pool into a focused, well-ordered context that maximizes model performance.

  • Query expansion - rewrite the user's query into multiple alternative phrasings
  • Multi-query retrieval - run several queries in parallel, merge and deduplicate results
  • HyDE - generate a hypothetical answer with the LLM, use it as the retrieval query to bridge the query-doc gap
  • Graph expansion - follow entity links in a knowledge graph starting from initial results
  • Multi-hop retrieval - iteratively retrieve; each step is informed by the previous results

Context Selection
Now we have too much information. What do we keep?
100 candidate chunks ↓ Need 10
Top-K Retrieval Similarity Thresholds Relevance Filtering Memory Retrieval
  • Top-K retrieval - keep the K highest-scoring chunks by embedding similarity
  • Similarity thresholds - discard any chunk below a minimum cosine score
  • Relevance filtering - use a cross-encoder or LLM judge to rerank and filter candidates
  • Memory retrieval - pull relevant long-term memories alongside document chunks
3
Context Compression
Still too large. How do we shrink it?
10 chunks · 20k tokens ↓ Need 5k tokens
Summarization Hierarchical Summaries Fact Extraction Context Distillation
  • Summarization - generate a concise summary of each chunk
  • Hierarchical summaries - summarize at multiple levels: sentence → paragraph → document
  • Fact extraction - extract only the key claims or assertions from each chunk
  • Context distillation - use a smaller model to condense context before passing to the main model
4
Context Pruning
What should be removed completely?
Some context adds zero value ↓ Remove it
Duplicate Chunks Irrelevant Memories Stale Context Old Tool Outputs
  • Duplicate chunks - deduplicate semantically identical or near-identical passages
  • Irrelevant memories - drop recalled memories that don't apply to the current query
  • Stale context - remove outdated information: old dates, superseded facts
  • Old tool outputs - trim tool results from early turns that no longer inform the current task

The same set of chunks can produce very different answers depending purely on their position. Ordering is free signal - use it deliberately.

This is the recommended default ordering - not a hard rule. Frameworks may vary (e.g. tool results before retrieval), but the key invariants are: system prompt first, current query last.

This arrangement leverages both the primacy effect (beginning) and recency effect (end) - the two positions where model attention is consistently highest.
