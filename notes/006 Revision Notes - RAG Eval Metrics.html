01

From TDD to EDD (Eval-Driven Development)

In traditional software engineering, Test-Driven Development (TDD) uses unit and integration tests with deterministic assertions (assert actual == expected). But in Generative AI and RAG applications, the system outputs non-deterministic natural language. Asserting exact string equality is impossible.

Instead, modern AI engineering adopts Eval-Driven Development (EDD). Before tuning chunk sizes, embedding models, vector databases, or prompt instructions, you build a benchmark dataset and define quantitative metrics. Any modification to your pipeline must demonstrably improve or maintain these eval scores.

Core Engineering Principle

"You cannot optimize what you do not measure." Without a repeatable evaluation harness, tweaking RAG parameters (top_k, chunk overlap, prompt engineering) is pure guesswork. EDD turns subjective prompt tweaking into verifiable, regression-tested engineering.

02

Building the Golden Dataset

A Golden Dataset is the ground-truth benchmark suite for your RAG system. It represents the questions real users ask and the verified answers they expect.

Golden Dataset Schema
{
  "question": "What happens if a user provides an incorrect password during login?",
  "reference": "AuthService.login in auth.py compares the submitted password against the stored plaintext password in _passwords dict. If they do not match, it raises AuthError('Invalid password').",
  "ground_truth_contexts": [
    "auth.py: AuthService.login(...) -> raises AuthError('Invalid password')"
  ]
}

Query Types to Include in Your Golden Set

Factoid Queries

Specific, single-hop lookups (e.g., "Where is _user_plans defined?"). Tests precision of direct semantic retrieval.

Comparison Queries

Comparing two concepts, classes, or endpoints (e.g., "Compare semantic search vs BM25 in our codebase"). Tests multi-chunk retrieval.

Procedure Queries

Step-by-step instructions (e.g., "How does task limit enforcement work in BillingService?"). Tests sequence preservation.

Summarization Queries

Broad, thematic overviews across entire modules. Tests high-level abstraction without lost context.

Adversarial / Negative Queries

Questions whose answers do NOT exist in the knowledge base. Tests the system's ability to refrain from hallucinating.

Methods of Dataset Creation

1. Synthetic Generation (LLM-Assisted)

  • Run an LLM over your ingested chunks to generate question-answer pairs automatically.
  • Fast and cheap; easily generates 100+ samples.
  • Risk: Can produce artificial, uniform queries that don't reflect true human usage.

2. Production Logs & Expert Curation

  • Collect real user queries from production monitoring (Langfuse, OpenLIT).
  • Flag queries with low user feedback (thumbs down) or failed tool calls.
  • Subject-matter experts write verified reference answers.
03

RAG Evaluation Architecture & Layers

A production RAG pipeline consists of multiple distinct stages. Evaluating only the end output makes diagnosis impossible. When an answer is wrong, is it because the retriever fetched irrelevant text, or because the LLM ignored the retrieved facts?

Decoupled Evaluation Architecture
1. Ingestion & Chunking Layer: Document parsing, AST chunking, semantic splitters.
↓
2. Retrieval & Ranking Layer: Vector search (Chroma, FAISS), BM25, Cross-Encoder Re-ranker.
Evaluated via: Precision@K, Recall@K, Hit Rate, MRR, NDCG (Deterministic, no LLM needed)
↓
3. Generation & Synthesis Layer: Prompt template, Context injection, LLM generation.
Evaluated via: Faithfulness, Answer Relevance, Factual Correctness (LLM-as-a-Judge)
04

Component 1: Retrieval Metrics (IR Metrics)

Retrieval metrics measure how effectively the search engine or vector database identifies relevant chunks from the corpus without needing any LLM call.

Precision@K Accuracy
Precision@K = |Relevant Retrieved| / K

Measures the proportion of retrieved chunks that are actually relevant. It answers: "How much noise and garbage did we inject into the prompt?"

Recall@K Completeness
Recall@K = |Relevant Retrieved| / |Total Relevant|

Measures the fraction of all relevant chunks in the knowledge base that were captured. It answers: "Did we miss any vital piece of evidence?"

Hit Rate@K Binary
Hit Rate = (Hit ≥ 1 ? 1 : 0) / N

The percentage of queries where at least one relevant document is present in the top-K retrieved list. A crucial baseline sanity check.

Mean Reciprocal Rank (MRR) First Hit Rank
MRR = (1 / |Q|) · Σ (1 / rank_i)

Focuses strictly on the position of the first relevant document. If rank is 1 → score 1.0; if rank 2 → 0.5; if rank 3 → 0.333.

NDCG@K Graded Order
NDCG@K = DCG@K / IDCG@K

Normalized Discounted Cumulative Gain handles graded relevance (e.g. 0=irrelevant, 1=partially relevant, 2=highly relevant) and applies a logarithmic position penalty.

Concrete Numerical Example (From Educosys Class):
Suppose a repository has 1,000 documents total, of which 100 documents are relevant to "Agentic System Design".
Your retriever fetches 50 documents (K=50). Upon inspection, 10 of those 50 are truly relevant.
• Precision: 10 / 50 = 20% (0.20)
• Recall: 10 / 100 = 10% (0.10)
05

The Precision vs Recall Trade-off

In RAG systems, tuning Top-K creates a direct engineering tension between Precision and Recall:

Extreme 1: Huge Top-K (e.g., K = 1,000)

  • Recall = 100/100 = 100% (All relevant chunks found).
  • Precision = 100/1,000 = 10% (900 chunks of garbage noise).
  • Consequences:
    • Skyrocketing token costs and latency.
    • "Lost in the Middle" syndrome — the LLM misses needles buried in haystacks.
    • High risk of context confusion and hallucination.

Extreme 2: Tiny Top-K (e.g., K = 1)

  • Precision = 1/1 = 100% (Pure signal, zero noise).
  • Recall = 1/100 = 1% (99% of relevant information omitted).
  • Consequences:
    • The LLM lacks sufficient context for complex or multi-part questions.
    • Forces the model to guess or return incomplete answers.

Optimal Engineering Balance

The production gold standard is a two-stage approach: Retrieve with high recall (Top 25-50) using vector + BM25 hybrid search, then apply a Cross-Encoder Re-ranker (Cohere, BGE-Reranker) to select the Top 3-5 highest-precision chunks for the LLM prompt.

Component 2: Generation Metrics & The RAG Triad

Generation metrics evaluate the quality of the LLM's response relative to the retrieved context and user query. Developed by TruLens and popularized by Ragas, the RAG Triad forms the core foundation:

User Query
Context Precision Query ↔ Context
Retrieved Context
Faithfulness (Groundedness) Context ↔ Answer
Generated Answer
Answer Relevance Query ↔ Generated Answer
1. Faithfulness (Groundedness) Context ↔ Answer

Measures if the answer is derived purely from the retrieved context without introducing external assumptions or hallucinations.

Calculation: Deconstruct the answer into discrete atomic claims. Use an LLM judge to verify if each claim is supported by the context.
Score = (Supported Claims) / (Total Claims)

2. Answer Relevance Query ↔ Answer

Measures how directly the response answers the question asked, without being evasive, verbose, or tangential.

Calculation: Prompt an LLM to generate 3 candidate questions that the response would answer. Compute cosine similarity between their embeddings and the original user query.

3. Context Precision Query ↔ Context

Evaluates whether the relevant chunks are positioned near the top of the context list.

Calculation: For each retrieved chunk, check if it was useful in answering the reference question. Higher weight is given to relevant chunks at rank 1 and 2.

4. Context Recall Reference ↔ Context

Measures whether all facts present in the ground-truth reference answer can be attributed to the retrieved context chunks.

Calculation: Context Recall = (Attributable Reference Sentences) / (Total Reference Sentences)

07

Critical Distinction: Correctness vs. Faithfulness

One of the most important concepts stressed in production RAG systems: Factual Correctness and Faithfulness are NOT the same thing.

Faithfulness (Groundedness)

  • Evaluates adherence to the provided retrieved document only.
  • Does NOT require a golden reference dataset.
  • Answers: "Did the model hallucinate beyond what it was given?"

Factual Correctness

  • Evaluates match against the true real-world ground truth.
  • DOES require a golden reference answer.
  • Answers: "Is the generated answer factually accurate in reality?"
The "Refund Policy" Scenario (from Lecture):
User Query: "What is the company refund policy?"
Retrieved Doc Chunks: "Under section 4.1, all digital purchases are strictly final. The company does not provide refunds under any circumstance."

Scenario A (LLM responds with real-world law):
"According to consumer protection regulations, you are entitled to a full refund within 14 days."
• Factual Correctness: High (in certain jurisdictions).
• Faithfulness Score: 0.0 (Unfaithful hallucination) — completely fabricated relative to the company's internal document.

Scenario B (Document contains an error):
Retrieved Doc states: "The capital of Australia is Sydney."
LLM responds: "The capital of Australia is Sydney."
• Faithfulness Score: 1.0 (100% faithful to context).
• Factual Correctness: 0.0 (Factually false in reality).
This diagnosis proves whether the bug is in your knowledge base or in your LLM generation!

This summary matrix outlines each metric, the layer it inspects, whether an LLM judge is required, and whether a golden reference dataset is needed:

Metric Primary Measurement Needs LLM? Needs Golden Reference? Target RAG Layer
Recall@K Completeness (are key chunks missing?) No Yes Retrieval
Precision@K Purity (how much noise was retrieved?) No Yes Retrieval
Hit Rate@K At least one relevant chunk found No Yes Retrieval
MRR Position of the 1st relevant document No Yes Retrieval / Ranking
NDCG@K Graded relevance and ranking decay No Yes Re-ranking

Implementation: Ragas with GPT-4o Evaluator

The following implementation mirrors the course repository (rag_evals/2_semanticrag_ast_eval.py). It runs automated evaluation using Ragas 0.4+ with GPT-4o as judge: 

import sys
from openai import OpenAI
from ragas import EvaluationDataset, SingleTurnSample, evaluate
from ragas.metrics._context_precision import LLMContextPrecisionWithReference
from ragas.metrics._context_recall import LLMContextRecall
from ragas.metrics._faithfulness import Faithfulness
from ragas.metrics._answer_relevance import AnswerRelevancy
from ragas.metrics._factual_correctness import FactualCorrectness
from ragas.llms import llm_factory
from langchain_openai import OpenAIEmbeddings

# 1. Assemble SingleTurnSample items from your RAG execution
samples = []
for tc in TEST_CASES:
    answer, contexts = run_agent(agent, tc["question"])
    samples.append(SingleTurnSample(
        user_input=tc["question"],
        response=answer,
        retrieved_contexts=contexts,
        reference=tc["reference"]
    ))

# 2. Configure LLM Judge and Embeddings
openai_client = OpenAI()
evaluator_llm = llm_factory("gpt-4o", client=openai_client)
lc_embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
eval_dataset = EvaluationDataset(samples=samples)

# 3. Execute Multi-Metric Evaluation
results = evaluate(
    dataset=eval_dataset,
    metrics=[
        LLMContextPrecisionWithReference(),
        LLMContextRecall(),
        Faithfulness(),
        AnswerRelevancy(embeddings=lc_embeddings),
        FactualCorrectness(),
    ],
    llm=evaluator_llm,
)

# 4. Generate Scorecard Table
df = results.to_pandas()
print("\n=== RAGAS EVALUATION SCORECARD ===")
for col in ["faithfulness", "answer_relevancy", "context_recall", "llm_context_precision_with_reference"]:
    avg = df[col].mean()
    status = "✅ PASS" if avg >= 0.70 else "❌ FAIL"
    print(f"{status} {col:<38}: {avg:.3f}")

Target Score Thresholds in Production

• Faithfulness ≥ 0.90: Hallucinations in high-stakes domains (legal, medical, financial) must be under 10%.
• Answer Relevance ≥ 0.85: Ensures users get concise, direct answers.
• Context Recall ≥ 0.80: Guarantees that at least 80% of necessary reference facts reach the LLM.
• Context Precision ≥ 0.75: Minimizes irrelevant context tokens.

Production Loop & Continuous Improvement

Evaluation does not end once the model is deployed. A production RAG system continuously improves through the following feedback loop:

1
Production Logging: Log all user prompts, retrieved chunks, and generated answers using OpenTelemetry, Langfuse, or LangSmith.
2
Triage Failures: Filter sessions with low online confidence scores, thumbs-down clicks, or user retry messages.
3
Human Review & Golden Set Expansion: Engineers diagnose the root cause (retrieval miss vs LLM hallucination), write the ground truth answer, and add it to the Golden Dataset.
4
CI/CD Regression Testing: Run the updated Ragas test suite on every pull request before merging changes to chunking or indexing pipelines.
