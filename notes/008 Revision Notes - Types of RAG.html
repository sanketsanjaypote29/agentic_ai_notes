Types of RAG Systems

A structured mental model for understanding how Retrieval-Augmented Generation systems are actually designed — from retrieval strategies to orchestration.

🧠

Mental Model

RAG techniques are often listed as if they're all equal alternatives — but they're not. Hybrid RAG is a retrieval strategy, Multi-Hop RAG is a reasoning strategy, Self-RAG is a validation strategy, and Agentic RAG is an orchestration strategy. They belong to different parts of the system. Every RAG system can be understood through these lenses:

Retrieval

  • Where does information come from?
  • Dense, Sparse, Hybrid, Graph, SQL, Web
  • Hierarchical, RAPTOR (index structuring)

Retrieval Improvement

  • How do we retrieve better information?
  • Query Rewriting, HyDE, Fusion

Reasoning

  • What if one retrieval isn't enough?
  • Multi-Hop, Reasoning RAG

Validation

  • Was retrieval good enough?
  • Self-RAG, Corrective RAG

Orchestration

  • How does the system decide whether, what, and when to retrieve?
  • Adaptive RAG, Agentic RAG
🔍

Retrieval

Where does information come from?

⬤ Naive RAG

The baseline: chunk documents, embed them, retrieve the top-K chunks by vector similarity, and pass them to the LLM. Everything else in this document is an improvement on top of this starting point.

⬤ Hybrid Retrieval

Hybrid Retrieval is not a specific retrieval technique — it is a retrieval architecture. It combines multiple retrieval strategies, each contributing different strengths. Results from all retrievers are merged and ranked using a ranking strategy to produce the final context. Common ranking strategies include Reciprocal Rank Fusion (RRF), which merges ranked lists without needing calibrated scores, and learned rerankers, which use a model to score relevance directly.

↓

→

↓

Any two retrieval strategies can be combined. The pairing is chosen based on the data and use case.

✅
Production Standard
Most production RAG systems use Hybrid Retrieval because no single retrieval strategy covers all query types well. Combining strategies gives more reliable coverage across the full range of user questions.

Index-time Structuring

How knowledge is organized before retrieval happens — the structure of the index determines what retrieval can find.

🏛

Stores information in levels of granularity. Search proceeds top-down, narrowing scope at each level.

Company

              └── Document
                    └── Chunk

Useful for very large, structured datasets like enterprise knowledge bases.

RAPTOR

Recursive Abstractive Processing for Tree Organized Retrieval

Problem: Chunk-level retrieval loses high-level meaning. Individual chunks don't capture document themes.

Solution: Build a summary tree bottom-up, then search top-down.

Chunks (level 0)
    ↓ summarize
Summary A  Summary B  (level 1)
    ↓ summarize
Summary of Summaries  (level 2)
    ↓ = root of tree

Retrieval Improvement

How do we retrieve better information?

⬤ Query Rewriting

Transform the user's raw query before hitting the retrieval layer. The goal isn't always to make the query more specific — different strategies reshape the query in different directions depending on what retrieval needs.

🎯
Query Rewriting

Make the query more specific and detailed so it better matches relevant documents.

"How does leader election work?"
→ "How does Raft leader election work?"
⬆
Step-back Prompting

Create a broader, more general query to retrieve background context before answering the specific question.

"Why does my Redis connection drop?"
→ "How does Redis handle connection timeouts?"
✂
Sub-query Decomposition

Break a complex query into multiple simpler sub-queries, each retrieving a piece of the answer.

"Compare auth approaches across our services"
→ "auth in service A" + "auth in service B" + ...

⬤ HyDE — Hypothetical Document Embeddings

Solves the query-document length mismatch: queries are short (5–20 tokens), documents are long (hundreds of tokens). HyDE generates a hypothetical answer first, then embeds that to search — much closer in the vector space to real documents.

🧪
Problem

Short queries live in a different part of the embedding space than long documents. This mismatch reduces retrieval quality.

Query: 5 tokens
≠
Doc: 500 tokens
✨
Solution
Short Question
↓ LLM generates
Hypothetical Answer (long)
↓ embed
Vector Search
↓
Real Documents

⬤ Fusion RAG & RRF

Generate multiple search queries from a single user question to improve recall, then fuse results using Reciprocal Rank Fusion (RRF).

⚙
Fusion RAG Flow
Original Query
↓ LLM generates variants
Query 1 + Query 2 + Query 3 + Query 4
↓ retrieve each
Result Sets 1–4
↓ RRF merge
Final Ranked List
📐
RRF Formula

RRF score for a document d across n ranked lists:

RRF(d) = Σ  1 / (k + rank_i(d))

k = 60  (smoothing constant)

Combines multiple rankings into one
without needing calibrated scores.
⚠
RRF is Fusion, NOT Re-ranking. It combines ranked lists. Re-ranking reorders a single result set using a separate model.

RRF in Fusion RAG vs. Hybrid Retrieval: both use RRF to merge result sets, but for different reasons. Fusion RAG uses it to merge results from multiple query variants run through the same retriever (query diversity). Hybrid Retrieval uses it to merge results from multiple retriever types (retriever diversity). RRF is just the merging mechanism — what's being merged is what differs.

The model critiques its own retrieval and generation. It asks itself whether it's confident and whether the retrieved content actually helped.

Self-reflection questions:

  • • Did the retrieved chunks actually help?
  • • Should I search with a different query?
  • • Is my generation faithful to the sources?

Corrective RAG (CRAG)

An external evaluator (not the generator itself) scores retrieval quality. If the retrieved content is poor, the system automatically corrects by re-retrieving or falling back to web search.

↓
Evaluator Scores Relevance
↓

External Evaluator Fallback Strategy
🔍
Self-RAG vs CRAG
Self-RAG: the generator model evaluates itself (internal critique). CRAG: a separate evaluator model checks retrieval quality (external critique). They can be combined — use CRAG to validate retrieval, then Self-RAG to validate generation.

Vectorless RAG

A design philosophy — spend more effort at index time so you need less semantic search at query time

Most RAG discussions assume a fixed pipeline: chunk → embed → vector DB → retrieve. Vectorless RAG asks: can we improve retrieval by structuring data better at index time instead of embedding everything? The intelligence moves from query time to indexing time.

⚠
Problems with Traditional RAG
  • Chunking destroys structure — relationships between methods, classes, and modules disappear when documents are split into flat chunks
  • Embeddings lose precision — searching for updateUser() may return createUser() and deleteUser() because they're semantically similar
  • Expensive indexing — generating and storing embeddings for millions of documents takes significant time and cost
💡
Core Idea

Instead of creating embeddings, create structure. Spend indexing time building explicit relationships, hierarchies, and graphs — so retrieval becomes navigation rather than semantic search.

Traditional RAG

Index: Generate Embeddings
↓
Query: Semantic Search

Vectorless RAG

Index: Build Structure
↓
Query: Follow Structure
💡
The Key Insight
At query time, the LLM doesn't run a vector search — it reasons about which index to navigate to next. Given a question, it decides: go to the HR node or the Finance node? Follow the uses edge or the owned_by edge? The intelligence is in the traversal decision, not in embedding similarity.

Real-world systems like Claude Code, Cursor, Codex, Deep Research, and enterprise AI agents combine techniques from multiple layers simultaneously. Understanding which layer a technique belongs to is what lets you design, debug, and reason about these systems clearly.
